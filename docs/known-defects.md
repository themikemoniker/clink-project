# Known defects

Findings from the slice 0–5 review that were **verified to still reproduce** and then
deliberately not fixed. This is the deferral ledger: everything here is a real behaviour of the
code on `main` today, with the reason it was left and the shape of the fix.

Line numbers were re-verified against the tree on **2026-08-20**, after the five review fixes
landed. `/docs/spike-findings.md` still wins on any protocol detail.

## Added by slice 7 (2026-08-21)

Same rules: verified to reproduce, deliberately not fixed, with the reason and the shape of the
fix. **Unlike every previous batch, two of these are on the money path** — that is what it costs
to have a path that writes rather than reads.

| what breaks | where | what it costs a user | why it is deferred | what fixing it looks like |
|---|---|---|---|---|
| **Losing `spike/.refunds.json` can pay a refund twice.** It is the only durable record of which oversells have been paid, because the node has none — there is no "already refunded" field on an invoice, and CLINK's `k1` turned out to be in-memory with a 5-minute TTL (findings §13.28). Delete the file, or run the watcher on a second machine, and every oversell it has already refunded is recomputed from the node as still owed. | `spike/refund.ts` (the journal), `spike/watch-sales.ts` `refundOversells` | A buyer paid twice for one oversell. Bounded by the node's frequency cap — the damage per interval cannot exceed it — but not prevented. | The alternatives are all worse or unbuildable today. The node cannot hold it. A relay could, but the watcher holds no signing key by design (spec §7.2), so it cannot publish a record of what it did. An encrypted NIP-78 document has the same problem. The honest answer is a local file, and the honest disclosure is this row. | Either (a) note the refund's payment hash back onto something the node *does* store — no field exists today, so this is an upstream ask; or (b) reconcile against the node's outgoing payments at startup, matching on amount and destination, which is a heuristic rather than a key. (b) is buildable now and is worth doing before this is used by anyone but its author. |
| **A `pending` refund is never resolved by the software, only reported.** If the node never answers a debit, the journal row stays `pending` forever: the watcher reprints it every five minutes and will not retry it, because retrying might double-pay and dropping it might strand a buyer. | `spike/watch-sales.ts` `refundOversells`, the `code === 0` branch | A refund that may or may not have been sent, and a person has to look at the node's outgoing payments to find out which. On a demo day that is a line in a terminal nobody is reading. | Deciding automatically means guessing about money, in a case where both guesses are wrong in a different direction. Refusing to guess is correct; making the human's job easy is a feature that was not in this slice. | Print the node's matching outgoing payments next to the pending row — `GetUserOperations` filtered by amount and time window — so the reconciliation is one glance rather than an investigation. Or a `--reconcile` mode that does it and asks. |
| **The LNURL half of the refund path has never resolved a real address.** All three settled invoices on the live node carry `@example.com` placeholders left by `check-buy.ts`, so `resolvePointer`'s LNURL branch is covered by unit tests on `lnurlpUrl` and by nothing on the wire. The noffer branch is proven, because it is `storefront/src/buy.ts` unmodified and that module has been paid with real money. | `spike/refund.ts` `resolvePointer`, the LNURL branch | A refund to a Lightning address could fail on a shape the LUD-06 validator gets wrong, and the failure mode is a `queued` row rather than a wrong payment — so it costs a delay and a manual handover, not money. | It needs a real settled sale carrying a real Lightning address, which needs a wallet and a person. The unit tests cover the URL construction and the response validation; what is unproven is one real host's JSON. | Buy `mugs` for 1,000 sats supplying a real Lightning address as the refund pointer, then engineer the oversell. That run also proves the whole slice end to end and is the demo beat — see `/docs/status.md`. |
| **`payDebit`'s success path has never returned `ok`.** Every debit driven so far was one the node refused — over the cap, or banned, or a k1 replay. That is exactly what `check-refund.ts` exists to prove and it is not the same as proving a payment lands. | `spike/ndebit.ts` `payDebit`, the `body.res === 'ok'` branch | Unknown. The branch is four lines and reads the same `{"res":"ok","preimage":…}` shape `clink-debits.md:178-217` specifies and that `sales-report.ts`-adjacent code already handles, but nobody has seen it. | It moves real money and the slice brief says to ask before that. | One 10-sat debit of an invoice the account issues to itself, or the real oversell test above. Both need a decision that is not the implementer's to make. |

## Documentation drift

A different kind of debt, listed so the eventual restructure has a target. **Nothing here was
fixed** — this section is a map, not a changelog.

**The pattern under all of them:** corrections land in the prose sections and the summary tables
keep the superseded answer. Every item below is a table, a diagram or a checklist row that a
later prose paragraph already overrules. A restructure that only rewrites prose will leave every
one of these standing.

**Slice 6 fixed the three it touched** (marked ☑ below) and left the rest, per the brief: fix the
drift you actually walk through, do not open a documentation project inside a build slice.

- **"One 24242 auth for the whole batch"** survives in three places, all contradicted by
  `spec.md:266` ("Dead — measured false in slice 1"), findings §9 (`spike-findings.md:809`:
  "one signed kind 24242 auth per blob. Do not batch.") and findings §13.11:
  - `docs/spec.md:508` — the §7.1 flow diagram
  - `docs/spec.md:1080` — the §11 question 9 row: "**Batching is permitted**"
  - `docs/spike-findings.md:1056` — the §12 corrections table: "one signature covers upload + mirroring"
- ☑ **React. FIXED 2026-08-21.** `spec.md` said both "no React, Tailwind or shadcn/ui" and, 116
  lines later, "the builder, which is React and can afford the SDK". Slice 6 owned the React
  decision, so it owned the drift: the second claim is struck and corrected, the §9 "revisit at
  slice 6" line is closed rather than deferred again, and `design.md`'s §5 heading and stack
  table now say what shipped. The answer is measured — the whole admin panel cost +4.3 KB gzip
  against React's ~45 KB floor.
- ☑ **Strict mode = delete the offer on depletion. FIXED 2026-08-21.** `spec.md` §11 q4 and
  `spike-findings.md` §12's §7.4 row both still said it. Slice 6 owned the "does mark sold delete
  the offer" decision, so it owned the drift: both rows now carry the decision that landed —
  nothing is done to the offer at all, the sold listing drops its `clink_offer` tag, and the
  invoice history stays readable for slice 7. Spec §7.4 itself is rewritten with the reasoning.
- **`docs/design.md` is a slice-0 document with one slice-5 patch.** §4 was updated for slice 5;
  the rest was not. §5 (`design.md:9`, `:103-105`) still specifies React + Tailwind + shadcn/ui
  and Radix; §2.5 (`design.md:62`) still specifies a blurhash or thumbhash placeholder, which
  `builder/src/listing.ts:54-57` deliberately does not write; §2.2 (`design.md:59`) and §3
  (`design.md:75`) still specify 1-bit dithered thumbnails.
- ☑ **The node account balance is both 6,000 and 8,000 sats. FIXED 2026-08-21, and measured
  rather than picked.** `node spike/sales-report.ts` reports **three settled invoices totalling
  8,000 sats** (`plants` 6,000, `mugs` 2×1,000) and `lncli listchannels` agrees on 8,000 local.
  The 6,000 figure was correct on the morning of 2026-08-21 and stale by that evening. All three
  `spec.md` sites now say 8,000, including §12 where it is the number slice 7's refund frequency
  cap gets set against — so that cap is now sized against a measured balance rather than a
  remembered one.
