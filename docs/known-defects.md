# Known defects

Findings from the slice 0–5 review that were **verified to still reproduce** and then
deliberately not fixed. This is the deferral ledger: everything here is a real behaviour of the
code on `main` today, with the reason it was left and the shape of the fix.

Line numbers were re-verified against the tree on **2026-08-20**, after the five review fixes
landed. `/docs/spike-findings.md` still wins on any protocol detail.

Most severe first.

| what breaks | where | what it costs a user | why it is deferred | what fixing it looks like |
|---|---|---|---|---|
| **Offer minting has no idempotency key.** `publish()` calls `createOffer` unconditionally, before anything is signed. Every failure after that point — a declined signature, a bunker timeout, a relay refusal — throws, and `main.ts`'s `finally` re-enables the Publish button. The seller presses it again and a **second payable offer** is minted for the same item. CLINK Manage `create` is explicitly not idempotent: "N identical requests create N offers" (clink-manage.md:226). `manage.ts:120` claims "the builder does that by minting only on a first publish" — nothing tracks whether a publish is a first one. | `builder/src/publish.ts:58-77`, re-enabled at `builder/src/main.ts:245`; the false claim at `builder/src/manage.ts:118-120` | A live, payable offer on the seller's node that no listing points at and no watcher watches, holding a buyer's stored `refund_pointer` under it. A buyer who reaches it pays into an item whose stock never moves. **This reads directly against `/CLAUDE.md`'s "every retry on the money path must be idempotent, keyed on a settlement identifier" — the retry here is keyed on nothing at all.** | It is new money-path code, and the money path is the one thing the review brief said not to touch on a follow-up pass. It also needs a Manage `list` action that `manage.ts` does not implement yet. | Dedupe by label before `create`, the way `spike/mint-offers.ts:64-91` already does over the native RPC: `list`, match on `label === listingD(slug)`, reuse the offer if it is there and the price agrees. Manage `list` filters on `management_pubkey` (findings §13.20) and the builder's own offers carry it, so `list` will in fact see a previous mint. |
| **A builder item with `stock 1` is still invisible to the watcher.** The 2026-08-20 fix reads the offer out of the rung's own `clink_offer` tag, which closed this for every multi-unit item. A one-unit item has exactly one rung — the stock-0 one — and `ladder.ts:47` `atStock` strips `clink_offer` at stock 0 by design. The fallback is `.offers.json`, which only `mint-offers.ts` writes and only for the fixture's items. | `spike/watch-sales.ts:80-92`, against `spike/ladder.ts:38-47` | The watcher logs `no decodable offer in its ladder or …/.offers.json — not watching` and skips the item. It sells, and the storefront keeps advertising it as available with a live Buy button — the oversell that slice 7 does not yet exist to refund. Most yard-sale items are one-of-a-kind, so this is the common case, not the edge one. | Fixing it means changing the shape of the ladder file, which `watch-sales.ts` reads and `publish.ts` writes — outside a five-fix follow-up, and it collides with slice 6's edit flow, which has to re-cut ladders anyway. | Carry the noffer on the ladder file itself rather than inferring it from a rung: `{ [d]: { units, noffer, steps } }`, written by `builder/src/publish.ts:144` and read first by `nofferOf`. Two lines each side, one file-format bump, and it makes `.offers.json` a pure fixture artefact. |
| **The NIP-46 client key is described as if it were disposable, and it is a bearer credential.** The comment calls it "not the seller's identity, it holds no funds, and burning it costs one re-approval". All three are true and together they are misleading: a NIP-46 grant is keyed to *this* pubkey, it is granted against the eight `sign_event` kinds in `PERMS`, and Amber stores a remembered grant with `acceptUntil = Long.MAX_VALUE`. It also survives Disconnect by design — `forgetBunker()` removes the bunker URI and keeps the key (`signer.ts:74-76`). | `builder/src/signer.ts:57-72` | Anyone who reads this localStorage value — a shared laptop, an XSS on the builder's own origin, a synced browser profile — can sign kind 30402 listings as the seller and mint kind 21003 offers on the seller's node, with **no further prompt on the phone**. The seller's own honest mental model of "the key is on my phone" stops being the whole story. | No code change was in scope, and there is no obviously better place to put it: a fresh key per session is the thing the comment correctly argues against. | Rewrite the comment to say what it is: a bearer credential to a standing signing grant, which survives Disconnect, and whose revocation is on the bunker side (Amber's app list), not here. Optionally have Disconnect offer to burn it. No behaviour change. |
| **Testnet, regtest and signet invoices are accepted.** `invoiceSats` matches `^ln(?:bc\|tb\|bcrt\|sb)…`, so an `lntb`/`lnbcrt`/`lnsb` invoice for the right number of sats passes the amount check and the page renders it as payable. | `storefront/src/offer.ts:121` | A buyer gets a QR their wallet refuses, with no explanation from us. Cost is a confused buyer at the table, not lost money — a mainnet wallet cannot pay a testnet invoice. | It can only happen if the seller's own node is misconfigured onto the wrong network, which is a state nothing else in the project tolerates either. | Drop the alternation to `^lnbc` and add one assertion to `storefront/src/offer.test.ts`. One character of regex; it was left out only to keep this pass to the five listed fixes. |
| **The one key in the project outside a Signer has no notice naming it.** `buy.ts` mints an ephemeral secret key per purchase. It is correct and CLINK requires it — the request is between the payer's key and the service, and the settlement receipt is encrypted to it — but every other rule-2 exception in the repo carries a `KEY HANDLING NOTICE` block (`spike/seed-listings.ts:3`, `mint-offers.ts:6`, `authorize-manage.ts:24`, `check-manage.ts:13`, `deploy-nsite.ts:21`). This one carries an ordinary comment. | `storefront/src/buy.ts:117` | Nothing at runtime. It costs a reader: a grep for `KEY HANDLING` — the way you would audit `/CLAUDE.md` rule 2 — returns five spike scripts and misses the only key in shipped browser code. | Documentation-only, and the code above it is right. | Promote the existing comment to a `KEY HANDLING NOTICE` block saying why an ephemeral per-purchase key is a rule-2 exception rather than a violation. |
| **Nothing reads `imeta`.** `builder/src/listing.ts:44-82` justifies each field by what the storefront will do with it — `x` "a content address the storefront can check a fetch against", `fallback` "in case `url` fails". `grep imeta storefront/src` returns one CSS comment (`style.css:141`) and no code. | written at `builder/src/listing.ts:72-82`, unread anywhere in `storefront/src` | Nothing today. It costs a reader again: the tag reads as load-bearing and is inert, and the `fallback` list — which the 2026-08-20 fix just made accurate — buys nothing until somebody consumes it. | Consuming it is real storefront work (hash-check a fetched blob, retry a failed image against `fallback`) with its own byte budget, and it is not on any slice. | Either add the `fallback` retry to the storefront's `srcset` path, or change the comment from "what the storefront will do" to "what a client could do" and say the tag is written for other clients. |
| **The two functions that decide how much stock is left cannot be tested.** `settledCount` (how many units sold) and `stepFor` (which pre-signed rung to publish) are the whole money-facing half of the watcher, and the file has top-level effects — three `existsSync` throws, a `connectPub`, an `await tick()` and a `setInterval` — so importing it runs it. Same for `imagesFor` and `tagsFor` in the seeder. | `spike/watch-sales.ts:124`, `:141`, effects at `:62-64`, `:111`, `:217`, `:224`; `spike/seed-listings.ts:190`, `:203` | Nothing directly — `ladder.test.ts` covers `targetStock`, and the 2026-08-21 real-money run exercised `settledCount` end to end. It costs future confidence: a change to either is unverifiable without spending sats. | Splitting a script into a module plus an entry point is a refactor across three files, and both scripts are demo infrastructure rather than shipped product. | Move the pure functions into `spike/ladder.ts` (which is already the tested module) and import them back. No behaviour change. |
| **The cheapest real test gap is `decodeNmanage`, and it has none.** It is a bech32 TLV parser on the money path — it decides which node pubkey the builder sends kind 21003 offer-mints to. Its sibling `decodeNoffer` in `storefront/src/offer.ts` has 10 tests and 43 assertions, 8 of those tests on the decoder alone. `decodeNmanage` has zero: its only non-UI caller is `spike/check-manage.ts:43`, which feeds it the real `.nmanage` file. Behind it, `storefront/src/render.ts` is **402 untested lines** including the buy state machine and the pointer validator; it needs a DOM, which is why the `LN_ADDRESS` bug shipped. | `builder/src/manage.ts:51-89`; `storefront/src/render.ts` (whole file) | A malformed or truncated `nmanage1…` that decodes to a *plausible* wrong pubkey would mint the seller's offers on somebody else's node. The code looks correct — bech32 checksummed, bounded, never throws — but nothing proves it stays that way. | `render.ts` needs a DOM harness, which is a new dependency and a new test style; that is a decision, not a follow-up fix. `decodeNmanage` is not — it is pure and importable. | `decodeNmanage`: add ~8 tests to a new `builder/src/manage.test.ts`, mirroring `offer.test.ts`'s cases (corrupt checksum, wrong prefix, truncated TLV, missing pointer, non-`wss://` relay). Half an hour, no new dependency. `render.ts`: separate decision. |

## Documentation drift

A different kind of debt, listed so the eventual restructure has a target. **Nothing here was
fixed** — this section is a map, not a changelog.

**The pattern under all of them:** corrections land in the prose sections and the summary tables
keep the superseded answer. Every item below is a table, a diagram or a checklist row that a
later prose paragraph already overrules. A restructure that only rewrites prose will leave every
one of these standing.

- **"One 24242 auth for the whole batch"** survives in three places, all contradicted by
  `spec.md:266` ("Dead — measured false in slice 1"), findings §9 (`spike-findings.md:809`:
  "one signed kind 24242 auth per blob. Do not batch.") and findings §13.11:
  - `docs/spec.md:508` — the §7.1 flow diagram
  - `docs/spec.md:1080` — the §11 question 9 row: "**Batching is permitted**"
  - `docs/spike-findings.md:1056` — the §12 corrections table: "one signature covers upload + mirroring"
- **React.** `docs/spec.md:671` says the builder ships with "no React, Tailwind or shadcn/ui";
  `docs/spec.md:787`, 116 lines later, says "the builder, which is React and can afford the SDK".
  `spec.md:17` and `:694` agree with the first.
- **Strict mode = delete the offer on depletion.** `docs/spec.md:1075` (§11 q4) and
  `docs/spike-findings.md:1052` (§12's §7.4 row) both still say it. Findings §13.17 disqualifies
  it — deleting the offer destroys the buyer's stored refund pointer — and the watcher does not
  do it (`spike/watch-sales.ts:94-109` says so at length). `spec.md:24` and `:591` already carry
  the correction.
- **`docs/design.md` is a slice-0 document with one slice-5 patch.** §4 was updated for slice 5;
  the rest was not. §5 (`design.md:9`, `:103-105`) still specifies React + Tailwind + shadcn/ui
  and Radix; §2.5 (`design.md:62`) still specifies a blurhash or thumbhash placeholder, which
  `builder/src/listing.ts:54-57` deliberately does not write; §2.2 (`design.md:59`) and §3
  (`design.md:75`) still specify 1-bit dithered thumbnails.
- **The node account balance is both 6,000 and 8,000 sats.** `docs/status.md:50-51` says 8,000
  (outbound, and the account balance); `docs/spec.md:152`, `:878` and `:1107` say 6,000 —
  including §12, where it is the number the slice-7 refund frequency cap is meant to be set
  against.
