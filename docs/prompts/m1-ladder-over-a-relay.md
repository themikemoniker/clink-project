One roadmap item, and it is the gate for the rest of milestone C. Item 11 and M2 both depend on
it, and the roadmap's own sequencing note says building D first means building parts of D twice.

The spine: **an edit should not require a human to move a file.** Today every edit, and restock
*is* an edit, ends at `builder/src/main.ts:366` telling the seller to save `.ladder.json` next to
`watch-sales.ts` and restart the watcher. Miss that step and either `isStale` refuses to watch the
item, or the watcher publishes rungs the relay silently drops and the item stays on sale after it
sold.

## The four decisions already taken, with their reasoning

Do not reopen these. They were taken deliberately in the previous session and the reasoning is
what makes them cheap to keep.

**1. The ladder is encrypted to a new third key, `spike/.watcher-key`.**
Not to the seller's own key, because the watcher would then need the seller's private key to open
it, which turns today's coincidence (the fixture seller and the node account are one identity)
into a permanent requirement, and spec §12 says that should be a separate key where possible.
Not to `.refund-key` either, because that is the spend credential under a node-enforced cap and
`watch-sales.ts:39-45` is explicit that the watcher's two keys are deliberately different. The new
key owns nothing, spends nothing and signs nothing. Its only power is decrypting ladders.

**2. The builder learns the watcher's pubkey by paste, the way `.nmanage` already works.**
Not by discovery. The builder must know which pubkey to trust *before* it encrypts, and
encrypting to an attacker's key hands them the lowest stock on every item, which is exactly what
the roadmap says must never become public. Generating the keypair in the builder is out under
rule 2. So the watcher prints its npub on first run and a human carries it once.

**3. One event per item, `d: lamppost-ladder-<slug>`, not one for the whole shop.**
Settled by measurement rather than assertion, and reproduced on 2026-08-26 on this machine. Regen
the Mérida ladder synthetically from `spike/merida-fixture.ts` (it is committed; `.merida-key.ladder.json`
is not) with three representative photo blobs per item:

| | whole-shop, 8 items |
|---|---|
| no photos | 28,739 bytes, 43.9% of NIP-44's 65,535-byte plaintext ceiling |
| **with photos** | **57,741 bytes, 88.1%**, and the mean per item puts the ceiling at **~9 items** |

Nine is the roadmap's predicted number and the same number the flyer holds (design.md §3). The
per-item figure is the one that matters for the design: the fattest item in that sale is `jabon`
at **19,906 bytes, 30% of the ceiling**, so per-item leaves roughly 3.3x headroom on the worst
real item. The binding cap is NIP-44's plaintext ceiling, not a relay's event size limit, which
was measured 2026-08-23 at 131,072 on nos.lol and about a million on damus and primal.

The `d` prefix collides with neither `clink-*`, which CLINK Beacon reserves on this kind
(clink-beacon.md:195, and the running Lightning.Pub still publishes a legacy `d = "Lightning.Pub"`
at `nostrPool.ts:53`), nor `lamppost-shop`, which `notes.ts` takes.

**4. Precedence, per item: relay wins when it decrypts, file is the cold-start fallback.**

```
relay ladder decrypts   -> use it
relay read FAILED       -> use the file, and warn loudly
no relay ladder at all  -> use the file
neither                 -> not watched, and named in the startup report
```

`isStale` runs on whichever ladder wins. The failure branch exists because
`spike/watch-sales.ts:204` already states the rule this must not break: *"the relay is down" must
not read as "your ladder is stale"*. Keep the file. Do not delete it.

## The design, as presented and pending your confirmation

**What M1 does and does not do.** It removes the file copy, the daemon restart and the
single-browser dependence. It does **not** make the watcher keyless: `.dev-key` is still the node
observe credential. Say this plainly wherever it is documented, because "the watcher holds no key"
is already a claim this project makes about *signing* and it must not blur.

**The event.** Kind 30078, one per item, `d: lamppost-ladder-<slug>`, authored by the seller,
content NIP-44 encrypted from the seller's key to the watcher's pubkey.

**The payload is the existing `LadderFile` entry unchanged**, `{units, noffer?, steps: Event[]}`
from `builder/src/publish.ts:44`. Same bytes on the relay as in the file, so precedence is a
straight swap and there is one parser rather than two.

**The trust chain is three layers and the third already exists.** The query filters
`authors: [SELLER]` and nostr-tools verifies signatures, so only the seller's own 30078s arrive.
NIP-44 decryption with (watcher private, seller public) succeeds only if the seller encrypted it.
And `stepFor` at `spike/watch-sales.ts:243` still verifies every rung independently before
publishing it, under the comment *"Never publish an event on the strength of where it was loaded
from."* So the transport change costs no new trust work at the publish moment. The genuinely new
surface is the bounded JSON parse of the decrypted plaintext, and `parseNotes` in
`builder/src/notes.ts` is the pattern to copy: cap the plaintext, cap the entry count, cap each
field, never throw, and read a corrupt payload as no ladder.

**It costs no new signer permission.** `sign_event:30078` (`builder/src/signer.ts:49`),
`nip44_encrypt` (`:41`) and `nip44_decrypt` have been in `PERMS` since slice 4, precisely so this
would not need a second bunker approval.

**It DOES cost one extra signature per item publish, and `approvalCount` has to say so.**
This is the same defect class the 2026-08-26 review caught on the fiat path: the number shown to
the seller and the events actually signed must be one number. Enforce it in `approvalCount` and at
the publish site, not by trusting call sites.

**Where the code goes**, chosen to preserve the existing dependency direction. `builder/` already
imports from `spike/` (`builder/tsconfig.json` includes `../spike/ladder.ts` and
`../spike/fixture.ts`); nothing in `spike/` imports from `builder/`. So:

| file | what lands |
|---|---|
| `spike/ladder.ts` | the shared keyless half: the kind constant, `ladderD(saleD, slug)`, the bounded payload parse, and a pure `chooseLadder(relay, file, relayFailed)` so precedence is testable without a relay |
| `builder/src/` | the publish half, plus the watcher-npub field and its `localStorage` handling |
| `builder/index.html` | the watcher-npub input and the sentence explaining what it is for |
| `spike/watch-sales.ts` | the subscribe half, the precedence call, the startup report |
| `spike/check-ladder-relay.ts` | new, on-demand, the real four-relay round trip under a throwaway key |

**Subscription is in scope, not just a startup read.** The watcher subscribes and re-checks on
every update rather than only at startup. That is what removes the *restart*, which is half of
what M1 is for.

## Testing

`npm test` stays offline, deterministic and free of side effects. Cover with ephemeral keys:
the `d` scheme, the bounded parse against oversized and malformed payloads, a real
encrypt/decrypt round trip, and **every branch of `chooseLadder`** including the relay-failed one.

`node spike/check-ladder-relay.ts` proves the real round trip on demand under a **throwaway** key:
publish one 30078, read it back from four relays, decrypt, diff against what went in. Free, needs
no seller key, and follows the shape `check-admin.ts` and `check-deploy.ts` already use.

**Watch every new assertion fail before you keep it.** That is this repo's standing discipline and
the last three sessions each recorded the red they produced in the commit message. Do the same.
